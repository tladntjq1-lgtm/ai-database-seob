# 2. 데이터베이스 안의 스키마와 테이블 관찰

## 2-1. 스키마 조회 결과

실행한 SQL:

​```sql
SELECT schema_name
FROM information_schema.schemata
ORDER BY schema_name;
​```

관찰한 스키마 이름 중 3개 이내를 적습니다.

​```text
1. information_schema
2. pg_catalog
3. public
​```

### `public`은 무엇인가요?

​```text
나의 설명:
public은 데이터베이스 안에 기본으로 존재하는 스키마 중 하나로, 스키마를
따로 지정하지 않고 테이블을 만들거나 조회하면 기본적으로 사용되는
스키마이다 (search_path에도 public이 포함되어 있었음).
​```

### 데이터베이스와 스키마는 같은 것인가요?

​```text
나의 설명:
아니다. 데이터베이스가 더 큰 단위이고, 그 안에 여러 스키마가 들어있는
구조이다. 지금 접속한 ax_evaluation 데이터베이스 안에도
information_schema, pg_catalog, public 등 여러 스키마가 함께 존재한다.
​```

## 2-2. 현재 보이는 테이블 조회

​```sql
SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_type = 'BASE TABLE'
  AND table_schema NOT IN ('pg_catalog', 'information_schema')
ORDER BY table_schema, table_name;
​```

​```text
조회된 사용자 테이블 수 또는 눈에 띈 테이블:
public 스키마에 71개 테이블이 있었다. account_emailaddress, accounts_user,
ai_evaluation, attendance_record, assignment 등 기존 프로젝트(동료평가
시스템)에서 쓰던 테이블들이 이미 존재했다.

아직 테이블이 거의 없어도 괜찮은 이유:
새로 PostgreSQL을 설치한 환경이라면 테이블이 하나도 없는 게 정상이다.
PostgreSQL이 설치되어 있다는 것과, 수업/프로젝트용 테이블이 이미
만들어져 있다는 것은 서로 다른 문제이기 때문이다. (나의 경우는 반대로
기존 프로젝트 DB를 그대로 쓰고 있어서 이미 71개 테이블이 존재하는
상태였다.)
​```

## 2-3. 관찰 정리

​```text
PostgreSQL 서버 안에는 여러 데이터베이스가 있을 수 있다.
한 데이터베이스 안에는 여러 스키마가 있을 수 있다.
스키마 안에는 테이블과 같은 객체가 존재한다.
​```

### `ch02_students`

### `ch02_enrollments`

| --- | --- | --- |
| `id` | 수강신청 한 건(행)을 구분하는 값 | PK |
| `student_id` | 이 신청을 한 학생을 가리키는 값 (ch02_students.id 참조) | FK |
| `course_id` | 이 신청이 어떤 강의인지 가리키는 값 (ch02_courses.id 참조) | FK |

## 3-3. 입력된 행 수

​```text
students 행 수: 3
courses 행 수: 2
enrollments 행 수: 3
​```

## 3-4. 내부 식별자와 업무 식별자

​```text
students.id가 필요한 이유:
DB 내부에서 각 학생 행을 빠르고 고유하게 구분하기 위해 필요하다. 이름
같은 값은 동명이인이 있을 수 있어 구분 기준으로 쓰기 어렵다.

student_number가 필요한 이유:
실제 학교 업무(성적 처리, 행정 문서 등)에서 학생을 식별할 때 쓰는 값이라,
DB 내부 값과 별도로 관리되어야 한다.

둘을 항상 같은 값으로 사용하지 않아도 되는 이유:
학번 체계는 학교 정책에 따라 나중에 바뀔 수 있고, 00123456처럼 앞자리
0을 보존해야 하는 값이라 내부 숫자 ID로 그대로 쓰기도 어렵다. 내부
식별자와 업무 식별자를 분리해두면, 학번이 바뀌어도 이미 연결된 FK
관계(수강신청 등)에는 영향을 주지 않는다.
​```

## 3-5. 숫자처럼 보이는 학번을 문자열로 저장한 이유

​```text
나의 설명:
학번(00123456)은 계산에 쓰는 숫자가 아니라 학생을 구분하기 위한 식별용
값이다. 숫자(INTEGER) 타입으로 저장하면 앞자리 0이 잘려나가 실제 학번과
다른 값이 되어버리기 때문에, 원래 모양 그대로 보존하려면 문자열(TEXT)로
저장해야 한다.
​```

# 4. 테이블과 조회 결과는 다르다

## 4-1. 원본 테이블 행 수

​```text
ch02_students 전체 행 수: 3
​```

## 4-2. 일부 열만 조회

​```text
원본 테이블의 열 수와 조회 결과의 열 수가 다른 이유:
SELECT에서 name, major 두 열만 선택했기 때문에 조회 결과에는 2개 열만
보이는 것이다. 원본 ch02_students 테이블에는 id, student_number, name,
major 총 4개 열이 그대로 존재하며, SQL은 그중 내가 선택한 열만 골라서
보여줄 뿐 원본 테이블 구조를 바꾸지 않는다.
​```

## 4-3. 조건을 적용한 조회

​```text
원본 테이블 행 수: 3
조회 결과 행 수: 2 (major = '컴퓨터공학'인 김민지, 박서연만 남음)
원본 테이블의 데이터가 삭제된 것인가?: 아니다
그렇게 판단한 이유: WHERE 조건에 맞지 않는 행(이준호, 데이터사이언스
전공)이 이번 조회 결과에서만 제외된 것이고, SELECT COUNT(*) FROM
ch02_students로 다시 확인하면 여전히 3명이 그대로 남아있기 때문이다.
​```

## 4-4. 정렬 결과 비교

​```text
ASC 결과의 첫 학생: 김민지
DESC 결과의 첫 학생: 이준호

이 실험을 통해 ORDER BY에 대해 알게 된 점:
ORDER BY로 정렬 기준을 명시하지 않으면 조회 결과의 순서가 항상 같다고
보장할 수 없다. 그리고 ORDER BY는 화면에 보여지는 결과의 순서만 바꿀
뿐이고, ASC로 정렬하든 DESC로 정렬하든 원본 테이블에 저장된 데이터
자체는 전혀 바뀌지 않는다는 것을 확인했다.
​```

# 5. PK와 FK를 실제로 관찰

## 5-1. 정상 데이터의 관계 읽기

다음 SQL 결과를 보고 작성합니다.

```sql
SELECT
    e.id AS enrollment_id,
    s.name AS student_name,
    c.title AS course_title,
    e.status
FROM ch02_enrollments AS e
JOIN ch02_students AS s
    ON s.id = e.student_id
JOIN ch02_courses AS c
    ON c.id = e.course_id
ORDER BY e.id;
```

```text
한 행이 의미하는 것:
특정 학생이 특정 강의를 신청한 사건 한 건을 의미한다. (예: enrollment_id
1001은 "김민지가 데이터베이스 입문을 신청했다"는 사건 하나)

같은 student_id가 여러 enrollment 행에서 반복될 수 있는 이유:
학생 한 명(김민지, id=1)이 여러 강의를 신청할 수 있기 때문이다.
(1001, 1002 두 행 모두 student_id=1)

같은 course_id가 여러 enrollment 행에서 반복될 수 있는 이유:
강의 한 개(데이터베이스 입문, id=10)에 여러 학생이 신청할 수 있기
때문이다. (1001, 1003 두 행 모두 course_id=10)

## 5-2. 기본키 중복 오류 관찰

실행 성공 / 실패: 실패
오류 메시지에서 확인한 핵심 단어: duplicate key, unique constraint, ch02_students_pkey, Key (id)=(1) already exists
왜 실패했다고 생각하는가: id=1은 이미 김민지 학생 행의 기본키(PK) 값으로 쓰이고 있는데, 같은 테이블 안에서 PK는 각 행을 고유하게 구분해야 하므로 동일한 PK 값(1)을 가진 행을 또 넣을 수 없기 때문이다.
```

## 5-3. 존재하지 않는 학생을 참조하는 FK 오류 관찰

존재하지 않는 `student_id`를 사용한 수강신청 입력 결과:

실행 성공 / 실패: 실패
오류 메시지에서 확인한 핵심 단어: foreign key constraint, ch02_enrollments_student_id_fkey, Key (student_id)=(999) is not present in table "ch02_students"
왜 실패했다고 생각하는가: student_id=999인 학생이 ch02_students 테이블에 존재하지 않는데, ch02_enrollments.student_id는 ch02_students.id를 참조하는 FK로 설정되어 있어서, 존재하지 않는 부모 행을 참조하는 관계는 DBMS가 막아준 것이다.
```
## 5-4. 정상 FK 반복 확인

​```text
student_id=2(이준호)가 이미 1003행에서 course_id=10을 신청한 상태였는데,
이번에 course_id=20도 추가로 신청했다. 같은 student_id 값이 반복해서
쓰였지만 정상적으로 입력됐다 — 학생 한 명이 여러 강의를 신청할 수 있는
1:N 관계이기 때문에 FK 값의 반복은 문제가 되지 않는다.
​```

## 5-5. PK와 FK의 차이 정리

​```text
PK는 같은 테이블 안에서 각 행을 고유하게 구분하기 위한 키이다.

FK는 다른 테이블(부모 테이블)의 행을 참조해서 두 테이블 사이의 관계를
연결하기 위한 키이다.

FK 값이 여러 행에서 반복될 수 있는 이유는
1:N 관계에서 "1" 쪽에 해당하는 값(학생 한 명, 강의 한 개)이 "N" 쪽의
여러 행(수강신청)에서 반복해서 참조될 수 있기 때문이다.
​```

## STEP 6. 1:N 관계 확인

### 6-1. GROUP BY 결과와 해석

| 기준 | 결과 |
|---|---|
| student_id별 신청 건수 | 1번(김민지) 2건, 2번(이준호) 2건 |
| course_id별 신청 건수 | 10번(DB101) 2건, 20번(PY101) 2건 |

- 한 학생이 여러 강의를 신청할 수 있고, 한 강의도 여러 학생이 신청할 수 있다.
- `student_id`, `course_id`는 FK지만 값이 반복되는 것이 정상이다. FK는 "유일함"을 보장하는 게 아니라 "참조 대상이 실제로 존재함"을 보장하는 제약이라는 걸 이 결과로 확인했다.
- ch02_students:ch02_enrollments = 1:N, ch02_courses:ch02_enrollments = 1:N 관계다. (학생과 강의만 놓고 보면 M:N이지만, 그 관계를 enrollments라는 별도 테이블로 풀어서 표현하고 있다.)

### 6-2. 아직 결정하지 않은 정책들

- 학생이 반드시 한 강의 이상 신청해야 하는가?
- 같은 학생이 같은 강의를 다시 신청할 수 있는가? (중복 신청 허용 여부)
- 신청을 취소하면 행을 삭제하는가, 아니면 status를 '취소'로 바꿔서 남기는가?
- 학생이 삭제되면 그 학생의 신청 기록은 어떻게 되는가? (같이 삭제 / 유지 / 삭제 자체를 막음)

# 7. AI가 만든 테이블 구조 직접 검토

## 7-1. AI에게 묻기 전에 내가 먼저 찾은 문제

```sql
CREATE TABLE student_courses (
    student_name VARCHAR(50),

# 10. 최종 개념 정리

```text
PostgreSQL은 관계형 데이터베이스를 관리하는 오픈소스 DBMS(데이터베이스 관리 시스템) 이다.

DBeaver 또는 psql은 PostgreSQL 같은 DBMS에 접속해서 SQL을 실행하고 결과를 확인하게 해주는 클라이언트 도구 이다.

데이터베이스와 스키마의 차이는 데이터베이스는 테이블들을 담는 가장 큰 단위이고, 스키마는 그 안에서 테이블들을 그룹으로 묶어 정리하는 더 작은 단위라는 것 이다.

테이블 한 행은 하나의 개별 데이터(사건이나 대상 하나)를 나타내는 단위 이다.

조회 결과가 원본 테이블과 다른 이유는 SELECT 결과는 조건(WHERE, JOIN, ORDER BY 등)에 따라 걸러지거나 재배열된 그 순간의 결과물일 뿐이고, 원본 테이블 자체는 그대로 남아있기 때문 이다.

내부 식별자와 업무 식별자의 차이는 내부 식별자(id)는 시스템이 행을 구분하려고 임의로 부여하는 값이고, 업무 식별자(학번 등)는 실제 업무에서 사람이 의미 있게 사용하는 값이라는 것 이다.

PK는 테이블의 각 행을 유일하게 식별하는 값으로, 중복되거나 비어 있으면 안 되는 제약 이다.

FK는 다른 테이블의 PK를 참조해서 두 테이블 사이의 관계를 연결하는 값으로, 참조 대상은 실제로 존재해야 하지만 값 자체는 반복될 수 있는 것 이다.
```
